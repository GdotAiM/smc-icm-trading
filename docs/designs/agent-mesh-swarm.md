## Problem Statement

Current trading analysis is manual and sequential. The auto_scheduler (15 scheduled events/day) and operator_loop (LLM-as-trader) exist but have been dormant since August 13-14. Only 1 paper trade has been placed in the system's history. The friction isn't finding setups — it's having to manually trigger analysis when opportunities form. A persistent, always-on agent swarm would catch and evaluate setups between scheduled scans without requiring human intervention.

## What Makes This Cool

You already have 9 deterministic engines, a 6-layer coherence stack, and LLM audit layers — all in Node.js. The novelty isn't building agents from scratch. It's creating a thin orchestrator that spawns each existing ict_agent (Python) as an isolated subprocess, feeds it your production engine outputs, lets agents compete on equal footing, and routes the winner through your existing execution path. The swarm doesn't replace what works. It multiplexes discipline across parallel analysts.

Key insight: your existing `scheduler_guard.cjs` already has a single-driver lock pattern. The swarm reuses that for coordination between agents instead of between schedulers. Same lock, different granularity.

## Constraints

- **Dual-language system:** smc-icm-trading is Node.js; ict_agent is Python. Bridge must be file-based or stdin/stdout.
- **Existing execution path is sacred:** `scheduler_guard.cjs` → `market_order.cjs` → TV CDP paper trading. Nothing replaces this.
- **Cross-pair SMT awareness lives in smc-icm-trading**, not ict_agent. Agents need it injected via shared state, not discovered natively.
- **Cost sensitivity:** Continuous full-swarm analysis across 5 pairs × 4 stages × retries could burn significant tokens. Event-triggered re-analysis (not polling) is required.
- **Crash isolation:** One agent crashing shouldn't take down others or block future cycles. Subprocess model mandatory.
- **No changes to existing operator_loop or auto_scheduler:** Both must keep working. Swarm is additive.

## Premises

1. Your existing auto_scheduler and operator_loop are dormant (since Aug 13-14) — adding complexity won't fix a persistence problem, but the underlying architecture is sound enough to build on.
2. Cross-pair SMT context matters and must be preserved through the bridge layer, not lost in agent isolation.
3. LLM costs are acceptable for event-triggered analysis but not for wasteful continuous polling.

## Approaches Considered

### Approach A: Bridge Layer (Conservative Swap)
Build `smci_bridge.py` loading engine JSON + TV CDP data as Python tools. Run ict_agent as sidecar per pair. Results feed back into ledger. No cross-agent coordination. Sequential still.
**Ruled out:** Doesn't achieve parallelism or competitive selection. Adds bridge code without the core value prop.

### Approach B: Node-Native Agent Swarm
Rewrite ict_agent's gated pipeline natively in Node.js. One language, direct engine access, native `Promise.all()` parallelism. Loses ict_agent's replay/fork/session management.
**Ruled out:** High integration risk during migration. Rewrites ~400 lines. Loses proven Python agent features (session replay, codegen gates) that would need rebuilding.

### Approach C: Agent Mesh (Hybrid Orchestration) ⭐ CHOSEN
Thin Node.js orchestrator (`tools/swarm/orchestrator.cjs`) manages worker pools. For each pair, spawns ict_agent subprocess with smc-icm-trading's engine JSON fed via stdin. Orchestrator runs all workers in parallel, ranks results by confluence score, passes top candidate to existing guard → execution path. Between scheduled scans, lightweight Node watcher polls TV WebSocket for price events and triggers agent re-evaluation only when relevant.
**Chosen because:** Zero changes to existing pipeline. Crash isolation via subprocess model. Event-triggered re-analysis cuts token costs 60-80% vs continuous polling. Competitive ranking gives explicit selection logic. Reuses ict_agent as-is (no rewrite).

### Component Breakdown

**1. `tools/swarm/orchestrator.cjs`** (~400 lines)
- `SwarmWorker`: wraps child_process for each ict_agent invocation
- `rankAgents()`: reads structured output from all workers, scores by confluence
- `injectSMTContext()`: merges cross-pair correlations from smc-icm-trading engine outputs
- `dispatchToExecution()`: passes winner to existing `scheduler_guard.cjs` → `market_order.cjs`
- Event loop: watches for price thresholds, schedules re-analysis only on triggers

**2. `tools/swarm/bridge.cjs`** (~200 lines)
- Converts smc-icm-trading's engine JSON format into ict_agent tool inputs
- `engineToCandles(pair, tf)`: reads `shared/<DATE>/<PAIR>/engine_<tf>.json` → pandas DataFrame
- `engineToStructure(pair, tf)`: extracts BOS/CHoCH/swings from engine output
- `engineToLiquidity(pair, tf)`: extracts BSL/SSL/equal highs/lows
- `engineToFVG(pair, tf)`: extracts fair value gaps
- `engineToOrderBlocks(pair, tf)`: extracts order blocks
- `engineToPdArray(pair, tf)`: extracts premium/discount state
- `wrapInSubprocess()`: pipes data to ict_agent's stdin, captures structured stdout

**3. `tools/swarm/watcher.cjs`** (~150 lines)
- Lightweight TV WebSocket subscriber for price events
- Triggers agent re-evaluation when: price enters kill zone, sweeps known liquidity pool, hits 15m structure break
- Debounces to avoid redundant analysis within 5-minute windows
- Writes trigger events to `shared/<DATE>/swarm_triggers.jsonl`

**4. New entries in `shared/<DATE>/` directory**
```
swarm_state.json        # Current rankings, active agents, last cycle
swarm_cycle_<ID>.jsonl  # Per-cycle agent transcripts
swarm_triggers.jsonl    # Event triggers (price-based re-analysis)
```

### Data Flow

1. **Scheduled cycle** (every 15 min during session hours):
   - Orchestrator reads latest engine outputs for all 5 pairs
   - Spawns 5 parallel Python subprocesses, each running ict_agent's chained loop
   - Each subprocess receives: symbol, timeframe config, engine JSON → stdin as JSON
   - Each agent produces: structured output (BIAS, DRAW_ON_LIQUIDITY, CONFLUENCE_SCORE, DECISION)
   - Orchestrator collects all results, ranks by confluence score
   - Top result routed to `scheduler_guard.cjs` for deterministic approval
   - If approved: `market_order.cjs` executes via TV CDP

2. **Event-triggered re-analysis** (between cycles):
   - Watcher detects price entering kill zone or sweeping liquidity
   - Writes trigger event to `swarm_triggers.jsonl`
   - Orchestrator picks up trigger, re-runs affected pair's agent
   - Skips pairs with no new triggers (token cost savings)

3. **Continuous monitoring mode** (optional, off by default):
   - Can run as background daemon: `node tools/swarm/orchestrator.cjs --daemon`
   - Self-restarting via node-supervisor or PM2
   - Health check writes heartbeat to `shared/<DATE>/swarm_heartbeat.json`

### Key Design Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Subprocess vs in-process | Subprocess (Python) | Crash isolation; ict_agent stays untouched |
| Communication | stdin/stdout JSON | No file sync race conditions; synchronous request/response |
| Parallelism | `child_process.fork()` with pool limit | 5 pairs max = no need for complex pooling |
| Cost control | Event-triggered only, not polling | 60-80% token savings vs continuous |
| Execution gate | Reuse `scheduler_guard.cjs` | Deterministic final word never replaced |
| SMT context | Injected from smc-icm-trading | Preserves cross-pair intelligence |
| Failure handling | Individual agent timeout (30s), skip, continue | One dead agent doesn't block others |

## Open Questions

1. **Memory persistence**: ict_agent uses SQLite for session memory. In subprocess mode, each agent gets its own DB connection. Should they share one DB file (risk of contention) or each have isolated memory (loses cross-session learning)? Recommendation: shared DB with WAL mode.
2. **Token budget cap**: Do we want a hard daily token limit that stops the swarm if it exceeds budget? (Yes recommended.)
3. **Replay compatibility**: Can `ict_agent replay <session.jsonl>` work when sessions are produced by the orchestrator subprocess? Needs testing.
4. **Discord alert integration**: Should swarm-triggered trades also post to Discord, or only operator_loop-triggered ones? Recommendation: both, with swarm prefix in message.
5. **Backtest support**: Can the swarm's competitive results be logged and later used as ground truth for backtesting? This would require saving all agent outputs (not just the winner).

## Success Criteria

1. Swarm runs 5 parallel agents, produces ranked results within 60 seconds total (vs 3-4 min sequential)
2. At least 1 trade placed per week during active sessions (London/NY hours)
3. Token cost stays under $20/day during active trading (event-triggered, not continuous)
4. Zero regressions to existing auto_scheduler or operator_loop functionality
5. Swarm can be started/stopped independently without affecting other systems
6. All agent transcripts logged to `shared/<DATE>/swarm_cycle_*.jsonl` for review
